## 1. What a process is

A **program** is a file on disk: code and initial data. A **process** is a program in execution plus everything the kernel tracks for it. The same program can be running as many processes. What the kernel keeps for each process:

| Part | What it is | Where you can see it |
|---|---|---|
| Identity | Process ID (PID), parent PID, process group, session, user and group IDs | `ps`, `/proc/PID/status` |
| Address space | The virtual memory the process can touch, with permissions per region | `/proc/PID/maps` |
| CPU state | Registers, program counter, stack pointer, FPU and vector state, when it is not running | Saved on its kernel stack |
| Open files | The table of file descriptors, each pointing at an open file description | `/proc/PID/fd` |
| Signal state | Handlers, the blocked set, pending signals | `/proc/PID/status` |
| Limits and accounting | Resource limits, CPU time, page faults, context switches | `getrusage`, `/proc/PID/status` |
| Scheduling state | State, priority, which CPU it last ran on | `ps`, `/proc/PID/stat` |

The abstraction gives each program the illusion of owning a private machine: a big flat memory and a CPU that is always its own. The kernel keeps the illusion by switching the CPU between processes and by mapping each address space onto physical memory.

### 1.1 The process control block in Linux

Textbooks call the kernel record a **process control block** (PCB). In Linux it is `struct task_struct` (from memory: defined in `include/linux/sched.h`; it is several kilobytes and has hundreds of fields). It does not hold everything inline; it points at separate objects that can be shared or replaced independently:

| Pointer in `task_struct` (from memory) | Object | Why separate |
|---|---|---|
| `mm` | `mm_struct`: the address space (list of memory regions, page-table root) | Shared by threads; replaced by `exec` |
| `files` | `files_struct`: the file-descriptor table | A thread group shares it, `fork` copies it |
| `signal`, `sighand` | Signal state | Shared by threads of one process |
| `cred` | Credentials (user and group IDs, capabilities) | Replaced when privileges change |
| `fs` | Current directory and root | `chroot`, `chdir` |
| `parent`, `children` | The process tree | For `wait` and re-parenting |

This split is why **a thread is just a `task_struct` that shares the same `mm`, `files` and `signal`** objects with another one; that is OS 03. A "process" in Linux is a thread group, and `Tgid` (thread group ID) is what users call the PID.

Read your own record from `/proc`. `/proc/self` means "the process that opens it", so the output shows the reader, here `grep`:

```text
Name: grep
State: R (running)
Tgid: 20588
Pid: 20588
PPid: 20585
Uid: 0 0 0 0
VmSize: 3728 kB
VmRSS: 2000 kB
Threads: 1
voluntary_ctxt_switches: 0
nonvoluntary_ctxt_switches: 1
```

`State: R (running)` is the reader itself (it is on the CPU). `VmSize` is the virtual size, `VmRSS` is the part resident in RAM (the man page notes this value is not exact). `voluntary_ctxt_switches` and `nonvoluntary_ctxt_switches` are the counters section 9 uses. `Uid` has four values (real, effective, saved, file system). The file descriptor table is visible as `/proc/self/fd`: on this machine descriptor 0 was a socket, 1 a pipe and 2 a file, the harness's choice; in a terminal they would all be the terminal device.

Process IDs are small integers drawn from a range with a maximum of 32768 here (`/proc/sys/kernel/pid_max`) and reused after a process is gone and reaped. PID 1 is the first user process; PID 2 is `kthreadd`, the parent of kernel threads (OS 01).

## 2. The address space of a process

On x86-64 Linux a program's address space looks like this, low addresses at the top (the regions of a 64-bit process, from memory for the general layout; the next program checks it):

| Region | Contents | Permissions |
|---|---|---|
| Text | The program's machine code | read, execute |
| Read-only data | String literals, `const` globals | read |
| Data | Initialised globals and statics | read, write |
| Bss | Zero-initialised globals and statics (not stored in the file) | read, write |
| Heap | `malloc` arena that grows with `brk` | read, write |
| Memory maps | Shared libraries, large `malloc` blocks, `mmap` regions | various |
| Stack | Call frames; grows toward low addresses | read, write |
| vDSO and vvar | Kernel-supplied code and data for fast calls (OS 01) | read, execute / read |

The program prints the address of an object in each region and checks the order, then shows its own `/proc/self/maps`:

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>

int initialised = 42;                   /* .data */
int zeroed;                             /* .bss */
const char rodata[] = "read only";      /* .rodata */

int main(void)
{
    int local = 0;                      /* stack */
    void *heap = malloc(64);            /* small malloc: the brk heap */
    void *big = malloc(1 << 20);        /* large malloc: its own mmap region */
    void *map = mmap(NULL, 4096, PROT_READ, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    printf("text     < rodata < data < bss < heap < mmap < stack : %s\n",
           (void *)main < (void *)rodata && (void *)rodata < (void *)&initialised &&
           (void *)&initialised < (void *)&zeroed && (void *)&zeroed < heap && heap < map && map < (void *)&local ? "yes" : "no");
    printf("large malloc is in the mmap area (above the heap): %s\n", big > heap ? "yes" : "no");
    printf("the stack is the highest of them: %s\n", (void *)&local > map && (void *)&local > big ? "yes" : "no");
    FILE *f = fopen("/proc/self/maps", "r");
    char line[256];
    printf("--- /proc/self/maps, shortened (addresses change on every run: ASLR) ---\n");
    while (fgets(line, sizeof line, f)) {
        char range[64], perms[8], off[16], dev[16], inode[16], name[128] = "";
        sscanf(line, "%63s %7s %15s %15s %15s %127s", range, perms, off, dev, inode, name);
        const char *tail = strrchr(name, '/');
        tail = tail ? tail + 1 : name;
        if (!strcmp(tail, "d5") || !strcmp(name, "[heap]") || !strcmp(name, "[stack]") || !strcmp(name, "[vdso]") ||
            !strcmp(name, "[vvar]"))
            printf("%-26s %s %s\n", range, perms, tail);
    }
    fclose(f);
    free(big);
    free(heap);
    return 0;
}
```

```text
text     < rodata < data < bss < heap < mmap < stack : yes
large malloc is in the mmap area (above the heap): yes
the stack is the highest of them: yes
--- /proc/self/maps, shortened (addresses change on every run: ASLR) ---
55b33d7c1000-55b33d7c2000  r--p d5
55b33d7c2000-55b33d7c3000  r-xp d5
55b33d7c3000-55b33d7c4000  r--p d5
55b33d7c4000-55b33d7c5000  r--p d5
55b33d7c5000-55b33d7c6000  rw-p d5
55b35c7b2000-55b35c8d3000  rw-p [heap]
7f240b948000-7f240b94c000  r--p [vvar]
7f240b94e000-7f240b950000  r-xp [vdso]
7fffa9f37000-7fffa9f60000  rw-p [stack]
```

How to read it:

- The order checks print `yes`: text below read-only data below data below bss below the heap below the mapped regions below the stack. A 1 MiB `malloc` landed *above* the heap, in the mapping area: glibc serves large requests with `mmap`, small ones from the `brk` heap.
- The executable shows five regions, not three: a read-only first page (the ELF headers, from memory), the code (`r-xp`), more read-only data, a read-only area after relocation (RELRO, a hardening feature) and the writable data and bss (`rw-p`). The linker separates them so each region can have its own permissions.
- Addresses begin with `55...` for the program (position-independent executable), `7f...` for libraries and the vDSO, `7ff...` for the stack. They are different on every run: **ASLR** (address-space layout randomisation, level 2 here) moves each base at `execve`.
- The permissions column `p` means a private mapping: a write is copy-on-write (section 6).

The address space is virtual. These regions are mappings the kernel records in `mm_struct`; physical pages are attached on first touch by the page-fault handler ([OS 01](01_os_structure_and_system_calls.md) showed 25,600 faults for 100 MiB; OS 09 covers the memory manager).

## 3. Process states

A process is always in one state. The textbook model has five: new, ready, running, waiting (blocked), terminated. Linux reports the same ideas in letters ([proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html), fetched):

| Letter | Meaning | Textbook state |
|---|---|---|
| `R` | Running or runnable (on the CPU or on a run queue) | Running, ready |
| `S` | Sleeping, interruptible: waiting for an event; a signal can wake it | Waiting |
| `D` | Disk sleep, uninterruptible: waiting for I/O; a signal cannot wake it | Waiting |
| `T` | Stopped by a signal (`SIGSTOP`) or a tracer | (stopped) |
| `Z` | Zombie: terminated, not yet reaped | Terminated |
| `X` | Dead (never seen in practice) | |

Notice that Linux does not distinguish "running" from "ready": both are `R`. A process on a run queue waiting for a CPU is `R` too, which is why the **load average** counts `R` and `D` processes (from memory).

Produce each one on demand: the parent forks a sleeper, a spinner, a process that stops itself on `SIGSTOP` and one that exits at once, and reads their state from `/proc/PID/stat`:

```c
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static char state_of(pid_t pid)
{
    char path[64], line[256], st = '?';
    snprintf(path, sizeof path, "/proc/%d/stat", (int)pid);
    FILE *f = fopen(path, "r");
    if (!f) return '-';
    if (fgets(line, sizeof line, f)) {
        char *p = strrchr(line, ')');   /* the command name can contain spaces and parentheses */
        if (p) st = p[2];
    }
    fclose(f);
    return st;
}

int main(void)
{
    pid_t sleeper = fork();
    if (sleeper == 0) { sleep(5); _exit(0); }
    pid_t spinner = fork();
    if (spinner == 0) { for (;;) ; }
    pid_t stopped = fork();
    if (stopped == 0) { for (;;) pause(); }
    pid_t dead = fork();
    if (dead == 0) _exit(0);
    usleep(100000);
    kill(stopped, SIGSTOP);
    usleep(100000);
    printf("sleeping in sleep()   : %c\n", state_of(sleeper));
    printf("spinning in a loop    : %c\n", state_of(spinner));
    printf("stopped by SIGSTOP    : %c\n", state_of(stopped));
    printf("exited, not yet waited: %c\n", state_of(dead));
    kill(spinner, SIGKILL); kill(stopped, SIGKILL); kill(sleeper, SIGKILL);
    while (waitpid(-1, NULL, 0) > 0)
        ;
    return 0;
}
```

```text
sleeping in sleep()   : S
spinning in a loop    : R
stopped by SIGSTOP    : T
exited, not yet waited: Z
```

Things to note in the code: the state is the character after the command name's closing parenthesis. The command name can contain spaces and parentheses, so the parser finds the *last* `)`. Using `sscanf("%s %s")` on the line is a classic bug. A `D` process cannot be killed (not even by `SIGKILL`) until the I/O returns, which is why a hung NFS mount leaves processes you cannot remove.

**State transitions:**

```text
              fork                 scheduler picks it
  (new) ------------> R (runnable) ---------------------> R (on CPU)
                         ^                                   |  |
          event arrives  |   time slice ends (preempted)     |  | waits for I/O, a lock, a timer
                         +-----------------------------------+  v
                         ^                                S or D (sleeping)
                         +-------------- event ---------------+
  R --SIGSTOP--> T --SIGCONT--> R              R --exit--> Z --parent's wait--> gone
```

## 4. `fork`: creating a process

`fork()` creates a new process that is a copy of the caller. It is called once and returns **twice**: in the parent it returns the child's PID, in the child it returns 0, and on failure it returns -1 in the parent and no child exists. ([fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html), fetched.)

```c
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    int x = 10;
    pid_t me = getpid();
    pid_t pid = fork();                 /* one call, two returns */
    if (pid < 0) {
        perror("fork");
        return 1;
    }
    if (pid == 0) {                     /* child: fork returned 0 */
        x += 1;                         /* the child has its own copy of x */
        printf("child : my parent is the process that called fork: %s, my pid differs: %s, x = %d\n",
               getppid() == me ? "yes" : "no", getpid() != me ? "yes" : "no", x);
        fflush(stdout);                 /* _exit does not flush stdio buffers */
        _exit(7);
    }
    int st;
    waitpid(pid, &st, 0);               /* parent: fork returned the child's pid */
    printf("parent: fork returned the child's pid: %s, status %d, my x = %d\n",
           pid != me && pid > 0 ? "yes" : "no", WEXITSTATUS(st), x);
    return 0;
}
```

```text
child : my parent is the process that called fork: yes, my pid differs: yes, x = 11
parent: fork returned the child's pid: yes, status 7, my x = 10
```

What the child gets, according to the man page: its own PID with the caller as parent; identical memory contents but a separate address space (later writes in one are invisible in the other, which `x` shows: the child printed 11, the parent still has 10); copies of the file descriptors that point at the **same open file descriptions**; an empty set of pending signals. Only the calling thread is replicated: the child starts with one thread, even if the parent had many. (Mutexes held by other threads stay locked in the child, which is why `fork` in a multithreaded program may only call async-signal-safe functions before `exec`.)

### 4.1 Shared open files

A descriptor is an index into the process's table; the table entry points to an **open file description** that holds the offset and flags. `fork` copies the table, not the descriptions. So parent and child share the file offset:

```c
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void)
{
    char path[] = "/tmp/os02_XXXXXX";
    int fd = mkstemp(path);
    write(fd, "0123456789abcdef", 16);
    lseek(fd, 0, SEEK_SET);
    char buf[8] = {0};
    pid_t pid = fork();
    if (pid == 0) {
        read(fd, buf, 4);                       /* the child reads 4 bytes through the inherited descriptor */
        printf("child  read \"%s\"\n", buf);
        fflush(stdout);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    read(fd, buf, 4);                           /* the parent continues where the child stopped */
    buf[4] = 0;
    printf("parent read \"%s\" (the offset is shared: parent and child hold one open file description)\n", buf);
    printf("offset now %ld\n", (long)lseek(fd, 0, SEEK_CUR));
    unlink(path);
    return 0;
}
```

```text
child  read "0123"
parent read "4567" (the offset is shared: parent and child hold one open file description)
offset now 8
```

The child read bytes 0 to 3, and the parent's next read continued at byte 4: one offset. This is how a shell's `cmd > file` and a pipeline work: descriptors set up before `exec` are inherited. The consequence: two processes writing to the same inherited descriptor interleave at the shared offset; they do not overwrite each other.

### 4.2 The stdio buffer is copied too

The program in Problem A prints with `printf`, forks twice and prints again. Without a terminal, stdout is fully buffered: a buffer that has not been flushed is part of the address space and is **duplicated** by `fork`. Output, with stdout a pipe:

```text
ABC
ABC
ABC
ABC
```

Four identical lines, not the `A`, two `B` and four `C` you might expect: each of the four processes ends up with `AB` in its buffer plus its own `C`, and each flushes the same text at exit. Flushing before the fork changes the result (`pa.c` with an argument, which flushes after every `printf`):

```text
ABBC
C
C
C
```

Now `A` appears once, `B` twice and `C` four times, as the number of processes that executed each statement. The order of the last lines is not guaranteed; it depends on which process the scheduler runs first.

A related bug found while writing this chapter's programs: a child that ends with `_exit` after `printf` printed **nothing** when stdout was a pipe. `_exit` ends the process without flushing stdio buffers, and the data was still in the buffer. `exit` (or `return` from `main`) flushes; `_exit` does not. The rule for a child that forked a copy of the parent's buffers: after `fork`, the child calls `_exit` (so it does not flush the parent's copy a second time), and flushes explicitly anything it wants written.

## 5. `exec`: replacing the program

`exec` (the family `execl`, `execvp`, ...) replaces the **program** a process is running. The PID, the parent, the open descriptors (unless marked close-on-exec) and the credentials stay. The address space is thrown away and rebuilt from the new executable; the stack and heap start fresh. A successful `exec` never returns; if it returns, it failed.

```c
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

/* fork then exec: the shell's whole job. The child replaces its program; the pid stays the same. */
int main(void)
{
    printf("before: pid %d\n", (int)getpid());
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) {
        char *args[] = {"echo", "echo runs in the same pid as the child", NULL};
        execvp("echo", args);
        perror("execvp");               /* reached only if exec failed */
        _exit(127);
    }
    int st;
    waitpid(pid, &st, 0);
    printf("parent: child (pid %s) exited with status %d\n", pid > 0 ? "from fork" : "?", WEXITSTATUS(st));
    return 0;
}
```

```text
before: pid 9457
echo runs in the same pid as the child
parent: child (pid from fork) exited with status 0
```

(The PID printed differs on each run.) This pair, `fork` then `exec` in the child, is how every shell starts a command.

**Why two calls instead of one `spawn`?** Between `fork` and `exec` the child is still your code, so it can rearrange its own state before the new program starts: redirect descriptors (`dup2`), change directory, drop privileges, set resource limits, join a process group. A single call would need arguments for all of those. Windows chose the other way (`CreateProcess` with many parameters); POSIX later added `posix_spawn` with attribute objects for the common cases (section 6.2). Section 8 shows the pipeline in Problem E, which relies on exactly this gap.

## 6. Copy-on-write and the cost of `fork`

Copying a 1 GiB address space on every `fork` would be absurd, especially since the child usually calls `exec` right away and throws the copy away. Linux therefore copies **page tables, not pages**: parent and child share the same physical pages, all marked read-only. The first write by either one raises a page fault; the handler allocates a new page, copies the 4 KiB into it, maps it writable in the writer's page table, and restarts the instruction. This is **copy-on-write** (COW). The 100 MiB experiment: the parent fills 100 MiB, forks, and the child reads every page, then writes every page, then writes them again.

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

static long minflt(void)
{
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(void)
{
    size_t size = 100u << 20, pages = size / 4096;
    char *p = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    memset(p, 1, size);                          /* the parent owns 100 MiB of real pages */
    int up[2];
    pipe(up);
    pid_t pid = fork();
    if (pid == 0) {
        long f0 = minflt();
        long sum = 0;
        for (size_t i = 0; i < size; i += 4096)
            sum += p[i];                         /* read every page */
        long f1 = minflt();
        for (size_t i = 0; i < size; i += 4096)
            p[i] = 2;                            /* write every page: copy on write */
        long f2 = minflt();
        for (size_t i = 0; i < size; i += 4096)
            p[i] = 3;                            /* now private: no more faults */
        long f3 = minflt();
        printf("pages: %zu (sum %ld)\n", pages, sum);
        printf("child faults reading every page:       %ld\n", f1 - f0);
        printf("child faults writing every page:       %ld\n", f2 - f1);
        printf("child faults writing the pages again:  %ld\n", f3 - f2);
        fflush(stdout);
        write(up[1], "x", 1);
        _exit(0);
    }
    char c;
    read(up[0], &c, 1);
    waitpid(pid, NULL, 0);
    printf("parent still sees its own data after the child wrote: %s\n", p[0] == 1 && p[size - 4096] == 1 ? "yes" : "no");
    return 0;
}
```

```text
pages: 25600 (sum 25600)
child faults reading every page:       0
child faults writing every page:       25600
child faults writing the pages again:  0
parent still sees its own data after the child wrote: yes
```

- **Reading shared pages costs no faults** (0): the mapping already exists and is readable.
- **Writing the first time costs one fault per page** (25,600 for 100 MiB): each is a page allocation and a 4 KiB copy.
- **The second write costs nothing**: the page is private and writable now.
- The parent's data is untouched (`yes`).

### 6.1 `fork` still costs time proportional to the parent's memory

COW avoids copying data, but the kernel still has to copy the **page tables** (and mark every writable page read-only, in both processes, from memory). That work is proportional to the amount of resident memory. Measurement: the parent holds a block of resident memory, then forks, the child exits at once and the parent waits.

```text
    1 MiB resident: fork+wait        96 us
   64 MiB resident: fork+wait      1530 us
  256 MiB resident: fork+wait      3315 us
 1024 MiB resident: fork+wait     13052 us
```

```c
#define _GNU_SOURCE
#include <spawn.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

extern char **environ;

static double now_ns(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1e9 + t.tv_nsec;
}

#define BEST(var, N, stmt)                                  \
    do {                                                    \
        var = 1e18;                                         \
        for (int rep = 0; rep < 3; ++rep) {                 \
            double t0 = now_ns();                           \
            for (int i = 0; i < (N); ++i) { stmt; }         \
            double d = (now_ns() - t0) / (N);               \
            if (d < var) var = d;                           \
        }                                                   \
    } while (0)

static void fork_wait(void)
{
    pid_t p = fork();
    if (p == 0) _exit(0);
    waitpid(p, NULL, 0);
}

static void vfork_wait(void)
{
    pid_t p = vfork();
    if (p == 0) _exit(0);
    waitpid(p, NULL, 0);
}

static void fork_exec_wait(void)
{
    pid_t p = fork();
    if (p == 0) { execl("/bin/true", "true", (char *)NULL); _exit(127); }
    waitpid(p, NULL, 0);
}

static void spawn_wait(void)
{
    pid_t p;
    char *args[] = {"true", NULL};
    posix_spawn(&p, "/bin/true", NULL, NULL, args, environ);
    waitpid(p, NULL, 0);
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);
    double t;
    BEST(t, 300, fork_wait());      printf("fork + wait, small parent (no large mapping)       %9.0f ns\n", t);
    BEST(t, 300, vfork_wait());     printf("vfork + wait, small parent                        %9.0f ns\n", t);
    BEST(t, 300, fork_exec_wait()); printf("fork + exec /bin/true + wait                      %9.0f ns\n", t);
    BEST(t, 300, spawn_wait());     printf("posix_spawn /bin/true + wait                      %9.0f ns\n", t);
    size_t sizes[] = {64u << 20, 256u << 20, 1024u << 20};
    for (int k = 0; k < 3; ++k) {
        char *m = mmap(NULL, sizes[k], PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        memset(m, 1, sizes[k]);
        BEST(t, 100, fork_wait());
        printf("fork + wait, parent with %4zu MiB resident        %9.0f ns\n", sizes[k] >> 20, t);
        BEST(t, 100, vfork_wait());
        printf("vfork + wait, parent with %4zu MiB resident       %9.0f ns\n", sizes[k] >> 20, t);
        munmap(m, sizes[k]);
    }
    return 0;
}
```

| `vfork` + wait, small parent | 33 / 34 |
| `fork` + `exec` `/bin/true` + wait | 831 / 864 |
| `posix_spawn` `/bin/true` + wait | 766 / 763 |
| `fork` + wait, 64 MiB resident | 2,080 / 1,102 |
| `vfork` + wait, 64 MiB resident | 44 / 36 |
| `fork` + wait, 256 MiB resident | 4,254 / 4,196 |
| `vfork` + wait, 256 MiB resident | 40 / 45 |
| `fork` + wait, 1 GiB resident | 14,521 / 13,488 |
| `vfork` + wait, 1 GiB resident | 31 / 35 |

How to read it:

- A `fork` from a small program costs about 80 to 100 µs. From a parent with 1 GiB resident it costs about 13 to 15 ms, **over 100 times more**, for a child that does nothing. The growth is roughly linear above 64 MiB (the 64 MiB figure was 1.1 ms in one run and 2.1 ms in another here, so small differences between runs are noise from the virtualised host). A server with a large heap that forks per request pays this per request.
- `vfork` costs the same regardless of size (30 to 45 µs here). It does not copy page tables at all: the child borrows the parent's address space, and the parent is suspended until the child calls `exec` or `_exit`. The child must do nothing but `exec` or `_exit` (it shares the parent's stack and memory, so any write is visible to the parent). Not a general tool.
- `fork` followed by `exec` of `/bin/true` costs about 830 to 865 µs: about **nine times** the small `fork` alone. The extra time is `exec` itself: opening the program, mapping it, the dynamic linker loading `libc` (about 30 system calls and page faults, OS 01 counted them for a `puts` program). Process creation is dominated by loading the new program, not by the `fork`, unless the parent is large.
- `posix_spawn`, which glibc implements with `clone(CLONE_VM | CLONE_VFORK)` (from memory), costs about 760 µs, a little less than `fork` + `exec` here, and does not grow with the parent's size. It is the portable way to start a program from a large process.

This explains known production behaviour: Redis snapshots by forking and letting COW freeze a consistent view while the parent keeps serving (and a write-heavy parent then copies many pages, so memory use can grow toward twice the data set; from memory, not measured here); a large JVM or Python service that shells out with `fork` + `exec` pays for page-table copying each time, which is why such programs use `posix_spawn` or a small helper process.

### 6.2 Overcommit

`fork` of a large process requires the kernel to promise the child as much memory as the parent has, though almost none of it will be copied. Linux's default overcommit mode (`/proc/sys/vm/overcommit_memory` is 0 here, heuristic) allows it unless it looks absurd. If that promise is later called in (every page written), the **OOM killer** picks a process to kill (OS 09).

## 7. `wait`, exit, zombies and orphans

When a process ends, the kernel frees its memory and descriptors but keeps a small record: the PID, the exit status and the resource usage. The record stays until the parent collects it with `wait` or `waitpid`. ([wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html), fetched.)

- A child that has terminated and not been waited for is a **zombie** (`Z`). It uses almost no memory but keeps its PID and a slot in the process table; if a parent leaks many, the table can fill and no new process can be created.
- The `wait` status packs the exit code and the reason. Use the macros: `WIFEXITED` (normal exit), `WEXITSTATUS` (the low 8 bits of the code), `WIFSIGNALED` (killed by a signal), `WTERMSIG` (which one). Never read the integer directly.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static void show(pid_t pid, const char *label)
{
    char path[64], line[256];
    snprintf(path, sizeof path, "/proc/%d/status", (int)pid);
    FILE *f = fopen(path, "r");
    if (!f) { printf("%-22s no /proc entry\n", label); return; }
    while (fgets(line, sizeof line, f))
        if (!strncmp(line, "State:", 6)) { line[strcspn(line, "\n")] = 0; printf("%-22s %s\n", label, line); }
    fclose(f);
}

int main(void)
{
    pid_t pid = fork();
    if (pid == 0)
        _exit(3);                       /* the child exits at once */
    usleep(200000);                     /* parent has not called wait yet */
    show(pid, "after child exit:");
    int st;
    waitpid(pid, &st, 0);               /* reaping removes the entry */
    show(pid, "after waitpid:");
    printf("exit code collected: %d\n", WEXITSTATUS(st));
    return 0;
}
```

```text
after child exit:      State: Z (zombie)
after waitpid:         no /proc entry
exit code collected: 3
```

After 200 ms with no `wait`, `/proc` showed the child as `Z`. After `waitpid` the entry was gone and the exit code 3 was collected. A zombie cannot be killed (it is already dead); the only fix is for the parent to `wait`, or for the parent to die so that someone else adopts and reaps it.

### 7.1 Orphans and adoption

If a parent exits first, its children are **orphans**. The kernel re-parents them: per the man page, to `init(1)` or to the nearest **subreaper** (a process that called `prctl(PR_SET_CHILD_SUBREAPER)`). That process waits for them, so orphans do not become permanent zombies. The program makes a process, which makes a child, which watches its parent ID before and after the middle process exits:

```c
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

/* The middle process exits first; its child is an orphan and the kernel gives it a new parent. */
int main(void)
{
    int up[2], down[2];                 /* synchronisation: the child reports, then the middle may exit */
    pipe(up);
    pipe(down);
    pid_t mid = fork();
    if (mid == 0) {
        pid_t kid = fork();
        if (kid == 0) {
            close(down[1]);             /* else this process would hold the pipe open itself */
            pid_t before = getppid();
            char c = 'x';
            write(up[1], &c, 1);        /* tell the middle process I have recorded my parent */
            read(down[0], &c, 1);       /* the middle process closes its end when it exits */
            usleep(100000);             /* give the kernel time to re-parent */
            pid_t after = getppid();
            printf("orphan: parent was the middle process: %s; parent changed: %s; new parent is pid 1: %s\n",
                   before > 1 ? "yes" : "no", after != before ? "yes" : "no", after == 1 ? "yes" : "no");
            fflush(stdout);
            _exit(0);
        }
        char c;
        read(up[0], &c, 1);             /* wait until the child has looked */
        _exit(0);                       /* exit without waiting: the child becomes an orphan */
    }
    close(down[1]);
    waitpid(mid, NULL, 0);
    usleep(400000);
    return 0;
}
```

```text
orphan: parent was the middle process: yes; parent changed: yes; new parent is pid 1: yes
```

The new parent was PID 1. A container usually runs its own application as PID 1 of the container's PID namespace; if that program does not reap adopted children, zombies accumulate (from memory; the reason container images often include a small init such as `tini`).

Two pipe rules from the code. It uses two pipes only to order the events (the child records its parent before the middle process exits). The first version of this program **hung**: the child held its own copy of the pipe's write end, so its `read` never saw end of file. A process must close the pipe ends it does not use, in every process that has them.

### 7.2 Exit status conventions

A shell reports `$?`: the exit code of the last command, 127 if the command was not found, and 128 plus the signal number if a signal killed it. Implement it with `fork`, `exec` and `wait` (Problem B):

```c
/* Problem B: run a command with arguments and report how it ended, like a shell does. */
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static int run(char *const argv[])
{
    fflush(stdout);
    pid_t pid = fork();
    if (pid < 0)
        return -1;
    if (pid == 0) {
        execvp(argv[0], argv);
        _exit(127);                         /* exec failed: the shell convention for "command not found" */
    }
    int st;
    if (waitpid(pid, &st, 0) < 0)
        return -1;
    if (WIFEXITED(st))
        return WEXITSTATUS(st);
    return 128 + WTERMSIG(st);              /* killed by a signal: the shell convention */
}

int main(void)
{
    char *ok[] = {"true", NULL};
    char *no[] = {"false", NULL};
    char *missing[] = {"no-such-command-xyz", NULL};
    char *sh[] = {"sh", "-c", "kill -TERM $$", NULL};
    printf("true            -> %d\n", run(ok));
    printf("false           -> %d\n", run(no));
    printf("missing command -> %d\n", run(missing));
    printf("killed by TERM  -> %d\n", run(sh));
    return 0;
}
```

```text
true            -> 0
false           -> 1
missing command -> 127
killed by TERM  -> 143
```

`false` returns 1 by convention; the missing command is 127 because the child's `exec` failed and it ran `_exit(127)`; the process killed by `SIGTERM` (signal 15) gives 143 = 128 + 15.

### 7.3 Avoiding zombies

Three ways, in order of how often they appear:

1. **`wait` for every child** (in a loop, or from a `SIGCHLD` handler that calls `waitpid(-1, ..., WNOHANG)` until it returns 0).
2. **Set `SIGCHLD` to `SIG_IGN`**: the man page says children then do not become zombies (and `wait` blocks until all children end, then fails with `ECHILD`).
3. **Double fork** for a daemon-style background job: the first child forks the real worker and exits immediately, the parent waits for only the first child, and the worker is adopted by init when its parent is gone. Problem C measures this.

## 8. A pipeline: `fork`, `pipe`, `dup2`, `exec` together

`ls /etc | sort | wc -l` is three processes connected by two pipes. The shell creates the pipes first, forks one child per stage, and in each child uses `dup2` to put the right pipe end on descriptor 0 or 1 before `exec`. The part that goes wrong is closing pipe ends (Problem E), because every process that keeps a write end open stops the reader from ever seeing end of file.

```c
/* Problem E: run "ls /etc | sort | wc -l" with pipes, the way a shell does. */
#include <stdio.h>
#include <sys/wait.h>
#include <unistd.h>

static pid_t spawn(char *const argv[], int in, int out, int close1, int close2)
{
    pid_t pid = fork();
    if (pid == 0) {
        if (in != 0) { dup2(in, 0); close(in); }        /* stdin from the previous stage */
        if (out != 1) { dup2(out, 1); close(out); }     /* stdout to the next stage */
        if (close1 >= 0) close(close1);                 /* close every pipe end this stage does not use */
        if (close2 >= 0) close(close2);
        execvp(argv[0], argv);
        _exit(127);
    }
    return pid;
}

int main(void)
{
    int p1[2], p2[2];
    pipe(p1);
    pipe(p2);
    char *a[] = {"ls", "/etc", NULL};
    char *b[] = {"sort", NULL};
    char *c[] = {"wc", "-l", NULL};
    pid_t k1 = spawn(a, 0, p1[1], p1[0], -1);
    close(p1[1]);
    pid_t k2 = spawn(b, p1[0], p2[1], p2[0], -1);
    close(p1[0]);
    close(p2[1]);
    pid_t k3 = spawn(c, p2[0], 1, -1, -1);
    close(p2[0]);
    int st;
    waitpid(k1, &st, 0);
    waitpid(k2, &st, 0);
    waitpid(k3, &st, 0);
    return 0;
}
```

```text
166
```

This printed 166, the same as the shell's own `ls /etc | sort | wc -l`. Measured negative control: the same program with the parent's `close(p1[1])` removed **hung** and was killed by `timeout` after 5 seconds, because `sort` waits for end of file on a pipe whose write end the parent still holds.

## 9. Context switch

A **context switch** takes the CPU from one thread to another. The kernel saves the outgoing thread's CPU state into its `task_struct` / kernel stack and loads the incoming thread's. What is involved (from memory for the list of items; the cost numbers below are measured):

1. **Registers**: general purpose registers, program counter, stack pointer, flags.
2. **Floating-point and vector state**: saved lazily or eagerly depending on the kernel.
3. **The kernel stack pointer**: each thread has its own kernel stack, so the switch is largely "swap the stack pointer and return".
4. **The page-table base** (`CR3` on x86-64): switching to a thread of a *different process* changes the address space. Switching between two threads of one process does not, which is why thread switches are cheaper.
5. **TLB state**: a new address space would need the TLB flushed; tagging entries with an address-space ID (PCID on x86) avoids most flushes ([CO 15](../04_computer_organization/15_virtual_memory_and_the_tlb.md)).
6. **Indirect costs**: the incoming thread finds the caches and branch predictors holding the outgoing thread's data, and runs slower until they warm.

The direct cost of the register swap is small; the indirect cost (cold caches and TLB) usually dominates and varies with what the thread does. In [OS 01](01_os_structure_and_system_calls.md) a one-byte pipe round trip between two processes on the same CPU measured about 1.7 µs. That round trip is four system calls and two context switches, so a switch plus its system calls costs well under a microsecond here. It is an upper bound for the switch, not a measurement of it alone.

### 9.1 Voluntary and involuntary

`/proc/PID/status` and `getrusage` count switches in two kinds ([proc_pid_status(5)](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html), fetched): **voluntary** when the process gave up the CPU itself (waiting for I/O, a sleep, a lock), **involuntary** when the kernel took it away (the time slice ran out, or a higher-priority task became runnable). A program shows both:

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/resource.h>
#include <time.h>
#include <unistd.h>

static void report(const char *what)
{
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("%-34s voluntary %6ld, involuntary %6ld\n", what, ru.ru_nvcsw, ru.ru_nivcsw);
}

int main(void)
{
    struct rusage a, b;
    getrusage(RUSAGE_SELF, &a);
    for (int i = 0; i < 50; ++i)
        usleep(2000);                                   /* gives up the CPU every time */
    getrusage(RUSAGE_SELF, &b);
    printf("50 sleeps of 2 ms: voluntary switches +%ld, involuntary +%ld\n", b.ru_nvcsw - a.ru_nvcsw, b.ru_nivcsw - a.ru_nivcsw);
    getrusage(RUSAGE_SELF, &a);
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    do { clock_gettime(CLOCK_MONOTONIC, &t1); } while ((t1.tv_sec - t0.tv_sec) * 1000000000L + (t1.tv_nsec - t0.tv_nsec) < 1000000000L);
    getrusage(RUSAGE_SELF, &b);
    printf("1 s of spinning:   voluntary switches +%ld, involuntary +%ld\n", b.ru_nvcsw - a.ru_nvcsw, b.ru_nivcsw - a.ru_nivcsw);
    (void)report;
    return 0;
}
```

Run 1:

```text
50 sleeps of 2 ms: voluntary switches +50, involuntary +0
1 s of spinning:   voluntary switches +0, involuntary +5
```

Run 2:

```text
50 sleeps of 2 ms: voluntary switches +50, involuntary +0
1 s of spinning:   voluntary switches +0, involuntary +2
```

Fifty sleeps gave exactly 50 voluntary switches and no involuntary ones: each sleep is one deliberate hand-over. One second of spinning gave no voluntary switches and a handful of involuntary ones (5 and 2: the count depends on what else wanted this CPU). A high voluntary count means the program is I/O or lock bound; a high involuntary count means it is CPU bound and competing for the CPU. That is the quickest first diagnosis for a slow process. Scheduling policy itself, who gets the CPU and when, is OS 04 and OS 05.

## What it costs

| Operation | Cost on this machine | Note |
|---|---|---|
| `fork` + `wait`, small parent | about 80 to 100 µs | Page tables of a small program |
| `fork` + `wait`, 1 GiB resident parent | about 13 to 15 ms | Page-table copy grows with resident memory |

| Voluntary context switch | one per sleep or block | 50 for 50 sleeps |

## Common mistakes

1. **Saying `fork` copies the memory.** It copies the page tables and shares the pages copy-on-write. The data is copied only as it is written.
2. **Saying `fork` is cheap.** It is cheap for a small process and proportional to resident memory for a large one: 13 to 15 ms at 1 GiB here.
3. **Calling a program and a process the same thing.** A program is a file; a process is an execution with state.
4. **Reading `wait` status as an exit code.** Use `WIFEXITED` and `WEXITSTATUS`; the status also holds the signal and flags.
5. **Not reaping children.** Each unreaped child is a zombie with a PID and a table slot.
6. **Trying to kill a zombie.** It is already dead; the parent must `wait`, or exit.
7. **Using `exit` instead of `_exit` in a forked child.** `exit` runs `atexit` handlers and flushes the parent's duplicated stdio buffers a second time. Use `_exit`, and flush what you actually want first.
8. **Using `_exit` and expecting buffered output.** The opposite: `_exit` does not flush. This chapter's own first demo lost its output that way.
9. **Forking with unflushed stdio.** The buffer is duplicated and printed twice (Problem A).
10. **Forgetting to close unused pipe ends.** The reader never sees end of file, and the pipeline hangs (section 8 and the orphan demo).
11. **Calling more than `exec` or `_exit` in a `vfork` child.** The child shares the parent's memory and stack; a write corrupts the parent.
12. **Using `fork` in a multithreaded program, then calling `malloc` or taking a lock before `exec`.** The child has one thread; a mutex held by another thread stays locked forever.
13. **Believing the child's PID is the parent's PID plus one.** PIDs are allocated from a pool and reused; never assume an order.
14. **Believing the state of a sleeping process is `R`.** It is `S` or `D`; `R` is on the CPU or on a run queue.
15. **Assuming `getppid()` is stable.** It changes to the adopter's PID when the parent exits.

## Questions out loud

1. **What is a process?** A program in execution: an address space, CPU state, open files, credentials and signal state, tracked by the kernel in a `task_struct` and its linked objects.
2. **Process versus program?** A program is the file; a process is a running instance; one program can be many processes.
3. **What does the kernel store per process?** Section 1's table: identity, address space, CPU state, descriptor table, signals, limits, scheduling state.
4. **Process states?** New, ready, running, waiting, terminated; Linux shows `R`, `S`, `D`, `T`, `Z`. Linux does not separate running and ready.
5. **What does `fork` do?** Creates a child that is a copy: new PID, a copy of the address space (copy-on-write) and of the descriptor table. Returns the child's PID in the parent and 0 in the child.
6. **What does `exec` do?** Replaces the program in the same process: same PID, fresh address space, descriptors kept unless close-on-exec.
7. **Why are `fork` and `exec` separate?** The child can set up descriptors, directory, limits and privileges between them. That is what a shell does for redirection and pipes.
8. **What is copy-on-write?** Share pages read-only after `fork`; copy a page on the first write. 25,600 faults for 100 MiB written, none for reads.
9. **Why is `fork` slow for a big process?** It must copy the page tables and write-protect every page. About 13 to 15 ms at 1 GiB resident, here.
10. **When use `vfork` or `posix_spawn`?** To start a new program from a large parent without copying page tables. `posix_spawn` is the portable choice.
11. **What is a zombie? What is an orphan?** A zombie is a terminated child not yet reaped; an orphan is a running child whose parent exited, adopted by init or a subreaper.
12. **How do you avoid zombies?** `wait` in a loop or from a `SIGCHLD` handler; ignore `SIGCHLD`; or double fork.
13. **What does a context switch save?** Registers, stack pointer, vector state, the page-table base; and what it costs indirectly (TLB, caches).
14. **Voluntary versus involuntary switch?** Gave up the CPU (blocked) versus preempted. They tell I/O-bound from CPU-bound.
15. **What is PID 1 for?** The ancestor of all user processes; it adopts orphans and must reap them.

**C.** Output of `pc.c`:

```c
/* Problem C: start a background child without leaving a zombie and without waiting for it (double fork). */
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

static int zombies_of_me(void)
{
    /* count children of this process whose state is Z by scanning /proc */
    char cmd[128];
    snprintf(cmd, sizeof cmd, "ps --ppid %d -o stat= | grep -c Z", (int)getpid());
    FILE *p = popen(cmd, "r");
    int n = 0;
    if (p) {
        if (fscanf(p, "%d", &n) != 1)
            n = -1;
        pclose(p);
    }
    return n;
}

int main(void)
{
    /* naive: fork a child that exits and never wait for it */
    if (fork() == 0)
        _exit(0);
    usleep(200000);
    printf("naive background child, not waited for: zombies = %d\n", zombies_of_me());

    /* double fork: the child forks the real worker and exits at once; the parent waits for the child only */
    pid_t mid = fork();
    if (mid == 0) {
        if (fork() == 0) {
            usleep(100000);
            _exit(0);                           /* the worker: its parent has already exited, so init reaps it */
        }
        _exit(0);
    }
    waitpid(mid, NULL, 0);
    usleep(400000);
    printf("after double fork, worker finished:     zombies = %d (the naive one is still there)\n", zombies_of_me());
    return 0;
}
```

```text
naive background child, not waited for: zombies = 1
after double fork, worker finished:     zombies = 1 (the naive one is still there)
```

The naive child is a zombie: the count is 1. After the double fork the count is still 1, and that 1 is the naive child, still unreaped: the double-fork worker added none. (The test uses `ps --ppid` to count children of the program that are in state `Z`.) The naive zombie disappears only when the program exits and init reaps it. The double-fork worker was adopted by PID 1 when its parent exited, so PID 1 reaped it.

**D.** `pd.c` takes the size as an argument; the numbers are in section 6.1. Fork+wait: about 100 µs at 1 MiB, 1.5 ms at 64 MiB, 3.3 ms at 256 MiB, 13 ms at 1 GiB. The cost is dominated by copying page tables and write-protecting the pages, proportional to resident memory. It is not the data size on disk or the virtual size: pages never touched cost nothing, which is why the test calls `memset` to make them resident. The time is per fork of a child that exits at once; there is no exec.

**E.** The solution is `pe.c` in section 8, output 166. Closing rules: in the parent, close each pipe end after the child that uses it has been forked (`p1[1]` after the first child, `p1[0]` after the second, `p2[1]` after the second, `p2[0]` after the third); in each child, after `dup2`, close the original descriptor and every other pipe end it inherited. A pipe delivers end of file only when **every** write end is closed. The measured failure: removing the parent's `close(p1[1])` made `sort` wait forever for end of file, and the program had to be killed after 5 seconds.

## Cheat sheet

| Topic | Fact |
|---|---|
| Process | Program in execution: address space, CPU state, descriptors, credentials, signals |
| Linux PCB | `task_struct`, pointing at `mm_struct`, `files_struct`, signal and credential objects (from memory) |
| States | `R` runnable/running, `S` sleep, `D` uninterruptible, `T` stopped, `Z` zombie |
| `fork` | Returns child PID in parent, 0 in child, -1 on error; copies page tables, pages copy-on-write |
| `exec` | Replaces the program; same PID; fresh address space; no return on success |
| `wait` | Collects status; frees the zombie; use `WIFEXITED` and `WEXITSTATUS` |
| Shell codes | 127 not found, 128 + n killed by signal n |
| Zombie / orphan | Dead and unreaped / alive and re-parented to init or a subreaper |
| COW | 25,600 faults for 100 MiB written, 0 for reads |
| `fork` cost here | About 90 µs small, about 14 ms with 1 GiB resident; `vfork` about 35 µs |
| Context switch | Registers, stack pointer, vector state, page-table base; indirect cost in TLB and caches |
| Switch counters | Voluntary = blocked; involuntary = preempted |
| Tools | `ps`, `/proc/PID/status`, `/proc/PID/maps`, `/proc/PID/fd`, `strace -f`, `getrusage` |
