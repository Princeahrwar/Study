## 1. What an operating system is

An OS does three jobs, and every topic in this track belongs to one of them.

| Job | What it means | Examples |
|---|---|---|
| Abstraction | Replace raw hardware with simple, uniform objects | A file instead of disk sectors; a process instead of "the CPU"; a socket instead of a NIC ring |
| Resource management | Share one machine between many programs fairly and efficiently | CPU scheduling, memory allocation, disk and network bandwidth |
| Protection | One program cannot read, corrupt or starve another, or the OS | Address spaces, permission checks, the user/kernel split |

The **kernel** is the part of the OS that runs with full hardware privilege and is always in memory. The **operating system** in the everyday sense is more: the kernel plus the system libraries, shell, init system and tools. On a phone or in a cloud VM you can have a kernel with almost nothing else. Look at the machine this tutorial ran on:

```text
Linux 6.18.44-fc-v445 x86_64, PID 1: process_api
processes: 67 lines of ps -e, kernel threads: 56 lines under kthreadd
    2 kthreadd
```

Two things to read there. PID 1 is not `systemd` or `init`; it is the program the kernel was told to run first (section 8). And the kernel has threads of its own: `ps` shows 56 lines of children of PID 2 (`kthreadd`), which are kernel threads (workers, the flusher threads that write dirty pages to disk, the RCU callbacks, per-CPU threads). A kernel thread has no user address space; it runs only in kernel mode. The point: "the kernel" is not a passive library. It is also a set of threads that do work on their own schedule.

**Kernel versus library.** `printf` is library code and runs in user mode. `write` is a thin library wrapper around the kernel's `write` system call. The test is simple: if it can run without special privilege and without crossing into the kernel, it is a library; if it touches shared hardware or other programs' state, it must be in the kernel (or in a privileged server process, section 6).

## 2. Protection: user mode and kernel mode

The CPU has at least two privilege levels. On x86 there are four **rings** (0 to 3), and every mainstream OS uses only ring 0 (kernel) and ring 3 (user). Arm calls them exception levels: EL0 is user, EL1 the kernel, EL2 a hypervisor, EL3 the secure monitor (from memory; [CO 26](../04_computer_organization/26_interrupts_exceptions_and_dma.md) and [CO 27](../04_computer_organization/27_hardware_virtualization.md) cover them). The current level is a few bits in a register that user code cannot write. The hardware enforces three things at ring 3:

1. **Privileged instructions fault.** `hlt`, `cli`/`sti` (interrupt flag), `in`/`out` (port I/O), loading control registers (`mov %cr0`), `wrmsr`, `lgdt` and similar raise a general-protection fault.
2. **Memory is checked on every access.** Each page-table entry has a "user" bit. Kernel pages have it clear, so a ring-3 access to them faults even though the kernel is mapped in the same address space ([CO 15](../04_computer_organization/15_virtual_memory_and_the_tlb.md)).
3. **The only way in is through gates the kernel set up.** User code cannot jump to an arbitrary kernel address at ring 0. It can only execute `syscall` (or `int`, or take an exception or interrupt), and the CPU then loads the entry point the kernel wrote into a register or table in advance.

Test all of it with a program. It forks one child for each forbidden action and reports how the child ended, so one crash does not stop the run. `rdtsc` (read the cycle counter) is the control: it is allowed, because the kernel leaves the `TSD` bit clear (from memory).

```c
#include <signal.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

/* Try something a user program is not allowed to do, in a child, and report how the child ended. */
static void attempt(const char *what, void (*fn)(void))
{
    fflush(stdout);
    pid_t pid = fork();
    if (pid == 0) {
        fn();
        _exit(0);                               /* reached only if the operation was allowed */
    }
    int st;
    waitpid(pid, &st, 0);
    if (WIFSIGNALED(st))
        printf("%-34s killed by signal %d (%s)\n", what, WTERMSIG(st), strsignal(WTERMSIG(st)));
    else
        printf("%-34s allowed, exit status %d\n", what, WEXITSTATUS(st));
}

static void do_hlt(void) { __asm__ volatile("hlt"); }
static void do_cli(void) { __asm__ volatile("cli"); }
static void do_cr0(void) { unsigned long v; __asm__ volatile("mov %%cr0, %0" : "=r"(v)); }
static void do_inb(void) { unsigned char v; __asm__ volatile("inb $0x60, %0" : "=a"(v)); }
static void do_rdtsc(void) { unsigned lo, hi; __asm__ volatile("rdtsc" : "=a"(lo), "=d"(hi)); }
static void do_kread(void) { volatile char c = *(volatile char *)0xffffffff81000000ul; (void)c; }
static void do_kwrite(void) { *(volatile char *)0xffffffff81000000ul = 1; }

int main(void)
{
    attempt("hlt (halt the CPU)", do_hlt);
    attempt("cli (disable interrupts)", do_cli);
    attempt("mov %cr0 (read a control register)", do_cr0);
    attempt("inb 0x60 (read an I/O port)", do_inb);
    attempt("read kernel address", do_kread);
    attempt("write kernel address", do_kwrite);
    attempt("rdtsc (read the cycle counter)", do_rdtsc);
    return 0;
}
```

Output:

```text
hlt (halt the CPU)                 killed by signal 11 (Segmentation fault)
cli (disable interrupts)           killed by signal 11 (Segmentation fault)
mov %cr0 (read a control register) killed by signal 11 (Segmentation fault)
inb 0x60 (read an I/O port)        killed by signal 11 (Segmentation fault)
read kernel address                killed by signal 11 (Segmentation fault)
write kernel address               killed by signal 11 (Segmentation fault)
rdtsc (read the cycle counter)     allowed, exit status 0
```

Every privileged action ends with signal 11, `SIGSEGV`. That surprises people who expect a different signal: on x86 a privileged instruction raises a general-protection fault (#GP), the kernel's fault handler sees it came from ring 3 and sends the process `SIGSEGV` (from memory for the exact mapping; the measured result is the signal 11). A page fault on a kernel address gives `SIGSEGV` too. `rdtsc` runs: not everything "low level" is privileged, and the kernel can choose (`prctl(PR_SET_TSC)`) whether to allow it.

**What "mode" really is.** There is no "kernel process". When your program calls `read`, the same thread, with the same address space and the same PID, continues executing, but in ring 0 on a different stack (the thread's **kernel stack**, one per thread, a few pages). When it returns, the CPU drops back to ring 3. The kernel runs *on behalf of* the process. That is why `top` shows "system" time for a process: the time its thread spent in ring 0.

## 3. Three ways into the kernel

Control enters the kernel in exactly three ways. A fourth, "a kernel thread was scheduled", is not a crossing at all (it was already in the kernel).

| Entry | Caused by | Synchronous? | Related to the running instruction? | Can it be delayed? | Example |
|---|---|---|---|---|---|
| System call | The program asks (`syscall`, `svc`) | Yes | Yes, it is the instruction | No, it is the request | `read`, `mmap`, `exit` |
| Exception (fault, trap) | The instruction cannot complete, or a debug trap | Yes | Yes | No | Page fault, divide by zero, `int3` breakpoint, privileged instruction |
| Interrupt | A device or timer outside the CPU | No | No | Yes: the CPU can mask it | Timer tick, NIC packet arrival, disk completion |

The split is what matters in an interview: *synchronous* events (system call, exception) happen at a definite instruction in the current thread, so the kernel handles them in that thread's context and may sleep. *Asynchronous* events (interrupts) arrive at an arbitrary point, belong to nobody in particular, and the handler must be short and may not sleep (Linux splits the work into a top half and a deferred bottom half; the driver details are for the drivers track).

Two of the three are visible from user space. Count the exceptions you cause by touching 100 MB of fresh memory (one **page fault** per 4 KiB page, from [CO 15](../04_computer_organization/15_virtual_memory_and_the_tlb.md)):

```c
#include <stdio.h>
#include <sys/mman.h>
#include <sys/resource.h>

static long minflt(void)
{
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;
}

int main(void)
{
    size_t size = 100u << 20;                         /* 100 MiB */
    char *p = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    long f0 = minflt();
    for (size_t i = 0; i < size; i += 4096)
        p[i] = 1;                                     /* first touch of every 4 KiB page */
    long f1 = minflt();
    for (size_t i = 0; i < size; i += 4096)
        p[i] = 2;                                     /* the pages are present now */
    long f2 = minflt();
    printf("pages in 100 MiB: %zu\n", size / 4096);
    printf("page faults during the first pass:  %ld\n", f1 - f0);
    printf("page faults during the second pass: %ld\n", f2 - f1);
    return 0;
}
```

```text
pages in 100 MiB: 25600
page faults during the first pass:  25600
page faults during the second pass: 0
```

Exactly one fault per page the first time (`mmap` only reserves addresses; the kernel allocates and zeroes a page on the first touch, inside the fault handler) and none the second time, because the page tables now hold the mapping. 25,600 exceptions took no instruction in your code to cause; the hardware raised them and the kernel resolved them and resumed the faulting instruction. A *fault* is restartable (the CPU saved the address of the instruction that failed, not the next one). That is also why an invalid access can be reported as a signal: the kernel looks at the cause and either fixes it (page fault on valid memory) or kills the process (`SIGSEGV`).

Interrupts are visible in `/proc`. Over one second of an almost idle machine, `/proc/stat` showed:

```text
78 interrupts, 65 context switches
```

The first number is interrupts handled, the second is context switches (both counted over the one second). The timer alone produces many; each device has its own line in `/proc/interrupts` (46 lines in that file on this VM).

A system call is **not** an interrupt in Linux terms, although the old x86 way to make one was `int 0x80`, a software interrupt. The fast `syscall` instruction replaced it because it skips the table lookup and the privilege checks of the interrupt gate.

## 4. The system-call mechanism

A system call is a controlled function call into the kernel. The ingredients are always the same:

1. A **number** that selects the service (a table index in the kernel).
2. **Arguments** in registers (never on the user stack, because the kernel must not trust a user stack pointer before it switches stacks).
3. A special instruction that raises the privilege level and jumps to a fixed kernel entry point. The kernel wrote that address into the CPU in advance (`MSR_LSTAR` on x86-64, from memory).
4. A **result** in a register, and a return instruction that drops back to user mode.

### 4.1 The x86-64 convention

| | x86-64 Linux |
|---|---|
| Instruction | `syscall` |
| Number | `rax` |
| Arguments 1 to 6 | `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` |
| Result | `rax` |
| Clobbered by the instruction | `rcx` (the return address), `r11` (the saved flags) |
| Return | `sysret` (kernel side) |

Note `r10`, not `rcx`, is the fourth argument: `syscall` overwrites `rcx`, which the normal C calling convention uses for argument four. That is why the C library wrapper moves `rcx` to `r10` first. The numbers in the kernel's header `asm/unistd_64.h`: `read` 0, `write` 1, `getpid` 39, `exit` 60, `openat` 257. The `man7` page [syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html) tabulates the instruction and registers for every architecture; it lists `syscall` with the number in `eax`, return in `rax` and arguments `rdi, rsi, rdx, r10, r8, r9` for x86-64.

**Errors.** The raw kernel interface has no `errno`. A failing call returns a value in the range -4095 to -1, which is `-errno`; anything else is a success value (a valid pointer from `mmap` can look "negative" as a signed number, which is why the cutoff is -4095 and not "any negative number"). The C library wrapper converts: it returns -1 and stores the positive code in `errno` (a thread-local). The man page says only "a -1 return value indicates an error, and an error number is stored in errno", which describes the library; the -4095 rule is what the kernel does and is from memory (it is `MAX_ERRNO` in the kernel source).

### 4.2 Make one yourself

This program issues system calls with inline assembly, no `syscall()` wrapper and no libc `write`. Compare the raw failure with what `open` reports:

```c
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <unistd.h>

/* The x86-64 system call convention: number in rax, arguments in rdi, rsi, rdx, r10, r8, r9.
   The syscall instruction overwrites rcx (return address) and r11 (saved flags). The result comes back in rax. */
static long sys3(long nr, long a, long b, long c)
{
    long ret;
    __asm__ volatile("syscall"
                     : "=a"(ret)
                     : "a"(nr), "D"(a), "S"(b), "d"(c)
                     : "rcx", "r11", "memory");
    return ret;
}

int main(void)
{
    const char msg[] = "written by a raw syscall\n";
    long n = sys3(SYS_write, 1, (long)msg, sizeof msg - 1);
    printf("raw write returned %ld\n", n);

    long pid_raw = sys3(SYS_getpid, 0, 0, 0);
    printf("raw getpid == getpid(): %s\n", pid_raw == getpid() ? "yes" : "no");

    /* The kernel reports an error as a small negative number in rax: -errno. */
    long r = sys3(SYS_openat, AT_FDCWD, (long)"/no/such/file", O_RDONLY);
    printf("raw openat of a missing file returned %ld (ENOENT is %d)\n", r, ENOENT);

    /* The C library turns that into -1 and sets errno. */
    errno = 0;
    int fd = open("/no/such/file", O_RDONLY);
    printf("open() returned %d, errno = %d (%s)\n", fd, errno, strerror(errno));

    /* Bad file descriptor: the same convention */
    r = sys3(SYS_write, 99, (long)msg, 1);
    printf("raw write to descriptor 99 returned %ld (EBADF is %d)\n", r, EBADF);
    return 0;
}
```

```text
written by a raw syscall
raw write returned 25
raw getpid == getpid(): yes
raw openat of a missing file returned -2 (ENOENT is 2)
open() returned -1, errno = 2 (No such file or directory)
raw write to descriptor 99 returned -9 (EBADF is 9)
```

The raw `openat` of a missing file returns -2, which is `-ENOENT`. The libc `open()` returned -1 with `errno` 2. Same event, two representations. The `"memory"` clobber matters: the kernel reads the message buffer, and without it the compiler may assume a store to the buffer is dead and delete it.

### 4.3 The same thing on Arm

Arm64 uses `svc #0` with the number in `w8`, arguments in `x0` to `x5`, and the result in `x0` ([syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html) table, which also shows the same error convention). The numbers differ because Arm64 uses the generic table: `read` 63, `write` 64, `openat` 56, `exit` 93, `getpid` 172 (from `asm-generic/unistd.h` on this machine). The numbers are part of the kernel's ABI, which is a stable promise: Linux does not renumber or remove a system call, because that would break every existing binary. This is what "Linux never breaks user space" means in practice, and it is why static binaries from decades ago still run.

### 4.4 A program with no C library

Everything the C library does at startup is optional. The smallest Linux program defines `_start` and talks to the kernel directly:

```c
/* A program with no C library: the entry point is _start and every service is a system call. */
static long sys3(long nr, long a, long b, long c)
{
    long ret;
    __asm__ volatile("syscall" : "=a"(ret) : "a"(nr), "D"(a), "S"(b), "d"(c) : "rcx", "r11", "memory");
    return ret;
}

void _start(void)
{
    static const char msg[] = "hello from a program with no libc\n";
    sys3(1, 1, (long)msg, sizeof msg - 1);      /* write(1, msg, len) */
    sys3(60, 0, 0, 0);                          /* exit(0) */
    for (;;)
        ;
}
```

### 4.5 Walk-through: what `read` does

1. User code calls the libc `read`, which puts 0 in `rax` and the arguments in the registers, and executes `syscall`.
2. The CPU sets ring 0, saves the user `rip` in `rcx` and flags in `r11`, and jumps to the kernel's entry point. It does **not** switch stacks (the kernel's first instructions do that: load this thread's kernel stack, save all the user registers there).
3. The kernel indexes its system call table with `rax`, calls the handler, which **validates every argument** (the descriptor exists, the buffer address is in the user half of the address space, the length is sane) and copies data with checked `copy_to_user`.
4. The handler may sleep (waiting for disk), in which case the scheduler runs another thread; this thread's kernel stack stays as it is.
5. The result goes in `rax`; the kernel restores the registers and executes `sysret`, back to ring 3, in the same thread.

Step 3 is the security boundary. The kernel treats everything from user space as hostile: a bad pointer must give `EFAULT`, not a kernel crash.

## 5. What a crossing costs

A system call is more than a function call: the mode switch itself, saving and restoring registers, argument validation, possibly flushing or switching page tables or branch predictors (the speculation mitigations), and the loss of cached state. Measure it with this program (`BENCH` repeats each loop three times and keeps the best):

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <sched.h>
#include <stdio.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

static double now_ns(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1e9 + t.tv_nsec;
}

static long sys0(long nr)
{
    long ret;
    __asm__ volatile("syscall" : "=a"(ret) : "a"(nr) : "rcx", "r11", "memory");
    return ret;
}

__attribute__((noinline)) static long plain_call(long x) { __asm__ volatile("" : "+r"(x)); return x + 1; }

static volatile long sink;
#define BENCH(name, N, stmt)                                   \
    do {                                                       \
        double best = 1e18;                                    \
        for (int rep = 0; rep < 3; ++rep) {                    \
            double t0 = now_ns();                              \
            for (long i = 0; i < (N); ++i) { stmt; }           \
            double d = (now_ns() - t0) / (N);                  \
            if (d < best) best = d;                            \
        }                                                      \
        printf("%-44s %9.1f ns\n", name, best);                \
    } while (0)

static double pingpong(int same_cpu, long rounds)
{
    int a[2], b[2];
    pipe(a);
    pipe(b);
    pid_t pid = fork();
    if (pid == 0) {
        cpu_set_t s;
        CPU_ZERO(&s);
        CPU_SET(same_cpu ? 0 : 1, &s);
        sched_setaffinity(0, sizeof s, &s);
        char c;
        close(a[1]);                          /* else this process keeps its own pipe open and never sees EOF */
        while (read(a[0], &c, 1) == 1)
            write(b[1], &c, 1);
        _exit(0);
    }
    cpu_set_t s;
    CPU_ZERO(&s);
    CPU_SET(0, &s);
    sched_setaffinity(0, sizeof s, &s);
    char c = 'x';
    double best = 1e18;
    for (int rep = 0; rep < 3; ++rep) {
        double t0 = now_ns();
        for (long i = 0; i < rounds; ++i) {
            write(a[1], &c, 1);
            read(b[0], &c, 1);
        }
        double d = (now_ns() - t0) / rounds;
        if (d < best) best = d;
    }
    close(a[1]);
    waitpid(pid, NULL, 0);
    return best;
}

int main(void)
{
    setvbuf(stdout, NULL, _IOLBF, 0);
    int zfd = open("/dev/zero", O_RDONLY);
    static char buf[4096];
    BENCH("plain function call (not inlined)", 20000000L, sink = plain_call(i));
    BENCH("clock_gettime (vDSO, no kernel entry)", 5000000L, { struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); sink = t.tv_nsec; });
    BENCH("raw syscall getpid (inline asm)", 2000000L, sink = sys0(SYS_getpid));
    BENCH("libc getpid()", 2000000L, sink = getpid());
    BENCH("syscall(SYS_clock_gettime) forced entry", 2000000L, { struct timespec t; syscall(SYS_clock_gettime, CLOCK_MONOTONIC, &t); sink = t.tv_nsec; });
    BENCH("read 1 byte from /dev/zero", 1000000L, sink = read(zfd, buf, 1));
    BENCH("read 4096 bytes from /dev/zero", 1000000L, sink = read(zfd, buf, 4096));
    printf("%-44s %9.1f ns\n", "pipe round trip, both processes on CPU 0", pingpong(1, 200000));
    printf("%-44s %9.1f ns\n", "pipe round trip, CPU 0 and CPU 1", pingpong(0, 200000));
    return 0;
}
```

| Operation | ns per call (run 1 / run 2) |
|---|---|
| Plain function call (not inlined) | 0.5 / 0.5 |
| `clock_gettime` through the vDSO | 21.3 / 21.7 |
| Raw `syscall` `getpid` (inline asm) | 81.4 / 80.7 |
| libc `getpid()` | 82.6 / 81.2 |
| `clock_gettime` forced through a real system call | 121.7 / 118.6 |
| `read` 1 byte from `/dev/zero` | 107.1 / 105.6 |
| `read` 4096 bytes from `/dev/zero` | 127.8 / 128.6 |
| Pipe round trip, both processes on one CPU | 1767.4 / 1711.2 |
| Pipe round trip, two different CPUs | 24351.6 / 23554.5 |

How to read it:

- The empty system call is about 80 ns, roughly 190 cycles at 2.3 GHz, 150 times a function call (the plain call is under a nanosecond because the loop is a call and an add). A "cheap" system call is cheap on the scale of a disk, expensive on the scale of arithmetic. A program doing 1 million tiny syscalls a second spends about 8% of one CPU in the crossing alone. Batching (`readv`, `writev`, `sendmmsg`, `io_uring`, covered in OS 15) exists to pay the crossing once for many operations.
- libc `getpid()` costs the same as the raw one (glibc 2.39 does not cache the PID in user space, as the equal timing shows).
- `clock_gettime` is about 20 ns, four times cheaper than `getpid`, because it **never enters the kernel**. The **vDSO** is a small shared object the kernel maps into every process; the kernel keeps the time data in a page that the vDSO code reads directly. On x86-64 it exports `__vdso_clock_gettime`, `__vdso_gettimeofday`, `__vdso_time` and `__vdso_getcpu` ([vdso(7)](https://man7.org/linux/man-pages/man7/vdso.7.html)); the kernel passes its address in the auxiliary vector as `AT_SYSINFO_EHDR`. Forcing the same call through `syscall()` costs about 120 ns, six times more (OS 15 covers the vDSO in depth). Observe it with `strace`: `clock_gettime` calls never appear.
- A read of 4096 bytes costs only about 20 to 35 ns more than one byte: the fixed crossing dominates, the copy of a page is small.
- A pipe round trip, one byte each way, is about 1.7 µs when both processes share a CPU and **13 to 15 times more** across CPUs (24 to 26 µs here). The two-CPU number is dominated by waking a process on another CPU: an inter-processor interrupt and, in a VM, a possible exit to the host. Pinning both to one CPU wins for ping-pong; it loses the parallelism. Treat the cross-CPU figure as specific to this micro-VM.

A bug that cost time while writing this: the first version of the benchmark **hung** because the forked child kept its own copy of the pipe's write end open, so its `read` never saw end of file when the parent closed the pipe. A process must close the pipe ends it does not use (OS 14 covers pipes).

**What the mitigations do here.** The kernel reports its protection state under `/sys/devices/system/cpu/vulnerabilities`. This guest says Meltdown "Not affected" (so no page-table switch on each system call, which is why the crossing is under 100 ns; on an older CPU with page-table isolation it costs hundreds of ns more), Spectre v2 "Mitigation: Enhanced / Automatic IBRS; IBPB: conditional", and branch-history injection (BHI) "Vulnerable". These settings and their cost are covered in [CO 30](../04_computer_organization/30_hardware_security.md); the lesson for this chapter is that a system-call cost is a property of *CPU plus kernel plus boot options*, never of "the system call".

## 6. Kernel architectures

The question is what runs in ring 0.

**Monolithic kernel.** Everything the OS needs (scheduler, memory manager, file systems, network stack, device drivers) is one program in one address space at ring 0. Components call each other as plain functions. Linux, the BSDs and Unix generally are monolithic. Advantage: speed, because a `read` through a file system and a block driver is function calls inside one kernel. Disadvantage: a bug in any driver can corrupt anything or crash the machine.

**Microkernel.** The kernel keeps only what must be privileged: address spaces, threads and scheduling, and inter-process communication (IPC). File systems, drivers and network stacks run as ordinary user processes ("servers"). A program asks the file server by sending it a message. Advantage: a crashed driver is a crashed process that can be restarted, the trusted code base is small enough to verify (seL4 has a machine-checked proof), and servers run with least privilege. Disadvantage: every service costs messages and context switches ([Wikipedia, Microkernel](https://en.wikipedia.org/wiki/Microkernel) says this directly: getting a service is more expensive than in a monolithic kernel, and first-generation microkernels such as Mach performed poorly; L4 cut IPC cost by more than an order of magnitude through careful design). Examples there: the L4 family, QNX, seL4, MINIX 3.

**Hybrid kernel.** A microkernel-inspired structure with more kept in kernel space for speed. Windows NT and Apple's XNU (a Mach kernel combined with BSD code) are named as hybrids in the same article. "Hybrid" is a loose marketing and architecture term; in practice most of the code of both runs in ring 0.

**Exokernel and unikernel** (from memory). An exokernel exports hardware resources almost raw and leaves abstractions to library operating systems linked into each application. A unikernel compiles one application together with just the OS libraries it needs into a single image that runs in one address space, usually directly on a hypervisor; no user/kernel split is needed because there is one program.

**Loadable modules and eBPF.** A monolithic kernel can still be extended at run time. Linux loads **modules** (kernel code, full privilege, no isolation, so a module is as trusted as the kernel itself; this machine boots with `nomodule`) and runs **eBPF** programs (code that the kernel verifies for safety before running it inside the kernel, so tracing and filtering do not need a module). Neither changes the architecture; they change how code gets in.

### 6.1 Measured: the price of "ask a server"

To see the shape of a microkernel's cost, this program does the same work two ways. Direct: one `read` of 4096 bytes from `/dev/zero`. Microkernel style: send a one-byte request over a pipe to a "file server" process, which does the `read` itself and sends the 4096 bytes back over a second pipe.

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

/* Monolithic: the application asks the kernel, one system call, the driver runs inside the kernel.
   Microkernel style: the application sends a request to a "file server" process, the server does the
   system call itself and sends the reply back. Same work, two extra messages and two context switches.
   This is NOT an optimised microkernel IPC (it uses pipes through a monolithic kernel), so it shows the
   shape of the cost, not what L4 or seL4 achieve. */
static double now_ns(void)
{
    struct timespec t;
    clock_gettime(CLOCK_MONOTONIC, &t);
    return t.tv_sec * 1e9 + t.tv_nsec;
}

static int xread(int fd, void *p, size_t n)
{
    char *c = p;
    while (n) {
        ssize_t r = read(fd, c, n);
        if (r <= 0)
            return -1;
        c += r;
        n -= (size_t)r;
    }
    return 0;
}

int main(void)
{
    enum { N = 100000, SZ = 4096 };
    static char buf[SZ];
    int req[2], rep[2];
    pipe(req);
    pipe(rep);
    pid_t pid = fork();
    if (pid == 0) {                                 /* the file server */
        close(req[1]);
        close(rep[0]);
        int zfd = open("/dev/zero", O_RDONLY);
        static char sbuf[SZ];
        char op;
        while (read(req[0], &op, 1) == 1) {
            read(zfd, sbuf, SZ);
            write(rep[1], sbuf, SZ);
        }
        _exit(0);
    }
    close(req[0]);
    close(rep[1]);
    int zfd = open("/dev/zero", O_RDONLY);
    double best_mono = 1e18, best_micro = 1e18;
    for (int rep_i = 0; rep_i < 3; ++rep_i) {
        double t0 = now_ns();
        for (int i = 0; i < N; ++i)
            read(zfd, buf, SZ);
        double d = (now_ns() - t0) / N;
        if (d < best_mono)
            best_mono = d;
        t0 = now_ns();
        for (int i = 0; i < N; ++i) {
            write(req[1], "r", 1);
            xread(rep[0], buf, SZ);
        }
        d = (now_ns() - t0) / N;
        if (d < best_micro)
            best_micro = d;
    }
    close(req[1]);
    waitpid(pid, NULL, 0);
    printf("read 4096 bytes, direct system call:        %9.0f ns\n", best_mono);
    printf("read 4096 bytes, through a server process:  %9.0f ns\n", best_micro);
    printf("ratio: %.0f times\n", best_micro / best_mono);
    return 0;
}
```

```text
run 1
read 4096 bytes, direct system call:              127 ns
read 4096 bytes, through a server process:      23720 ns
ratio: 187 times
run 2
read 4096 bytes, direct system call:              132 ns
read 4096 bytes, through a server process:      23592 ns
ratio: 178 times
```

The server path costs **about 175 to 190 times more** than the direct system call. Read this carefully:

- The extra cost is two pipe messages (each a system call, a copy, a wake-up) and two context switches, all going through a monolithic kernel that is not designed for this. A real microkernel's IPC is a tuned primitive (L4 and seL4 pass short messages in registers and switch directly to the receiver). This program shows what an *un*optimised design costs, not what a good microkernel costs.
- The time is wake-ups and context switches, not data copying: the 4 KiB copy is small next to the scheduling.
- A real microkernel system keeps the hot paths short (drivers can be given direct hardware access, shared memory avoids copies) and accepts a few percent overhead in exchange for isolation. The honest summary: monolithic is faster when it is not buggy; microkernel buys fault containment and a small trusted base at the price of IPC performance that has to be engineered.

## 7. The address space the kernel shares with you

On x86-64 Linux (from memory) each process has one address space, and the kernel lives in the **top half** of it (the canonical high addresses starting `0xffff...`). The user program uses the low half (up to `0x00007fffffffffff`). The kernel is mapped into every process (from memory) so that a system call does not need to switch page tables: the same `CR3` stays loaded and only the privilege level changes. The user-bit rule from section 2 keeps user code out: reading `0xffffffff81000000` raised `SIGSEGV` in the demo of section 2.

The cost of that layout is that a CPU bug that leaks data across the privilege boundary through speculation (Meltdown) lets user code read kernel memory the mapping contains. The fix, kernel page-table isolation, unmaps most of the kernel while user code runs and so makes each crossing switch tables, which is the large cost on affected CPUs (from memory; this guest is not affected, as section 5 shows). **ASLR** (address-space layout randomisation; level 2 here) randomises the stack, heap, library and vDSO addresses per `execve`, and the kernel's own base (KASLR); it makes exploits guess.

## 8. How Linux boots

From power-on to the first process, in order:

1. **Firmware** (BIOS or UEFI) tests the hardware, picks a boot device and loads a boot loader (from memory).
2. **The boot loader** (GRUB, systemd-boot) loads the kernel image and an initial RAM file system (`initramfs`) into memory, passes the **kernel command line**, and jumps to the kernel (from memory).
3. **The kernel decompresses itself**, sets up paging and CPU state, and runs the C entry point `start_kernel`, which initialises memory management, the scheduler, interrupts and timers, then mounts the initial root file system from the initramfs and brings up devices (from memory).
4. **It runs the first user-space program**, `/init` from the initramfs or the program named by `rdinit=`; if there is no initramfs, it mounts the real root file system (`root=`) and runs `/sbin/init` (from memory; the [kernel's initrd documentation](https://www.kernel.org/doc/html/latest/admin-guide/initrd.html) describes the older initrd mechanism where `/sbin/init` runs and mounts the real root file system, then moves to it with `pivot_root` and execs the real `/sbin/init`). That program is **PID 1**.
5. PID 1 starts everything else (services, login). It is the ancestor of every user process and the adopter of orphans. If PID 1 exits, the kernel panics (from memory).

**The machine you are on skipped most of that.** It is a Firecracker micro-VM that boots the kernel directly: no firmware menu, no boot loader, no UEFI (`/sys/firmware/efi` does not exist; only `acpi` and `memmap` are there). The real log (the `dmesg` timestamps are seconds since boot):

## Common mistakes

1. **Saying the kernel is a process.** It is code that runs in the context of whichever thread entered it, plus its own threads.
2. **Calling a system call an interrupt.** It is a synchronous request from the running thread. Interrupts come from devices and are asynchronous.
3. **Saying page faults are errors.** Most are normal (first touch, copy on write, file mapping, swap in). Only a fault the kernel cannot resolve becomes `SIGSEGV`.
4. **Expecting `strace` to show every library call.** It shows system calls only; `printf`, `malloc` and `clock_gettime` (vDSO) may produce none or few.
5. **Forgetting that libc buffers.** `puts` to a file or pipe makes one `write` for many lines; to a terminal it makes one per line.
6. **Treating any negative return as an error in a raw system call.** Only -4095 to -1; `mmap` returns high addresses that look negative.
7. **Checking `errno` after a success.** `errno` is meaningful only after a call that reported failure.
8. **Omitting the `"memory"` clobber, or `rcx` and `r11`, in inline assembly for `syscall`.** The compiler then keeps values in registers the instruction overwrites, or reorders around the call.
9. **Using the C calling convention for the fourth system call argument.** It is `r10`, not `rcx`.
10. **Believing a microkernel is slow by definition.** The first generation was; tuned IPC (L4, seL4) is not. The cost depends on the IPC design.
11. **Believing a monolithic kernel has no structure.** It has layers and interfaces; the difference is that they share one privilege domain.
12. **Not closing unused pipe ends after `fork`.** The reader never sees end of file; this tutorial's own first benchmark hung that way.
13. **Writing a freestanding program and letting the compiler call `strlen`.** With `-nostdlib`, a hand-written `len` loop can be turned into a call to `strlen` and fail to link (section 9 and Problem E).
14. **Quoting a system call cost without the CPU and the kernel.** Mitigations change it by a large factor.

## Questions out loud

1. **What is the difference between user mode and kernel mode?** The CPU runs at a privilege level. At the lower one, privileged instructions fault and kernel pages are not accessible; at the higher one everything is allowed. The kernel runs at the higher level, programs at the lower one, and the only way up is through gates the kernel set up.
2. **How does a program ask the kernel for a service?** It puts the system call number and arguments in registers and executes `syscall` (x86-64) or `svc` (Arm64). The CPU enters the kernel at a fixed address, the kernel validates the arguments, does the work, and returns through `sysret` with the result in `rax`.
3. **Why is `r10` used instead of `rcx` for the fourth argument?** `syscall` writes the return address into `rcx`.
4. **How is an error reported?** The kernel returns `-errno`, the C library turns it into -1 with `errno` set.
5. **System call, exception, interrupt: what are the differences?** Section 3's table. Synchronous or not, caused by the instruction or not, maskable or not.
6. **What happens on a page fault?** The CPU saves the faulting instruction's address and enters the kernel's fault handler. The kernel decides if the address is valid (first touch of anonymous memory, file-backed page, copy on write) and if so maps a page and restarts the instruction. If not, it sends `SIGSEGV`.
7. **Why does `clock_gettime` not need a system call?** The vDSO. The kernel maps a small shared object and a time data page into each process, and the function reads the data in user mode.
8. **What does a system call cost and why is it not free?** About 80 ns here: the mode switch, register save and restore, argument validation, and mitigations; it also disturbs caches and branch predictors. Batch to amortise.
9. **Monolithic versus microkernel?** Section 6: one privilege domain versus servers; speed versus isolation and a small trusted base.
10. **Why is Linux monolithic but still extensible?** Modules and eBPF.
11. **What is a hybrid kernel?** A microkernel-derived design with much of the OS in kernel space for performance; Windows NT and XNU.
12. **Walk me through Linux boot.** Firmware, boot loader, kernel decompress and `start_kernel`, initramfs, mount root, run PID 1.
13. **What is PID 1 and why is it special?** The first user process; it starts the rest, adopts orphans, and the kernel panics if it exits.
14. **How do you make a program with no libc?** `_start` as the entry, system calls by inline assembly, `-nostdlib -static`, and `-fno-builtin` to stop the compiler emitting calls to library functions.

**A.**

2. Interrupt, asynchronous: from a device.
3. System call, synchronous: requested by the program.
4. Exception (divide error), synchronous: caused by the instruction. Linux delivers `SIGFPE`.

**B.** The wrapper and its output (the `-4095` cutoff separates errors from large values):

```c
/* Problem B: a write wrapper over the raw system call with the libc error convention. */
#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>

static long raw_write(int fd, const void *buf, unsigned long n)
{
    long ret;
    __asm__ volatile("syscall" : "=a"(ret) : "a"(SYS_write), "D"((long)fd), "S"(buf), "d"(n) : "rcx", "r11", "memory");
    return ret;
}

/* Like write(2): -1 and errno on error, the byte count otherwise. */
static long my_write(int fd, const void *buf, unsigned long n)
{
    long r = raw_write(fd, buf, n);
    if (r < 0 && r >= -4095) {
        errno = (int)-r;
        return -1;
    }
    return r;
}

int main(void)
{
    long a = my_write(1, "ok\n", 3);
    long b = my_write(77, "x", 1);
    int e = errno;
    printf("%ld %ld errno=%d (%s)\n", a, b, e, strerror(e));
    return 0;
}
```

```text
ok
3 -1 errno=9 (Bad file descriptor)
```

Descriptor 77 does not exist, so the kernel returns -9 (`-EBADF`) and the wrapper stores 9 in `errno`.

**C.** Redirected to a file (or a pipe), the run showed:

```text
40 calls, 2 errors
```

Those figures are with stdout redirected, so the library buffered the three `printf` lines into one `write`. Counting groups, from the earlier `strace -c` of this program: `execve` 1; dynamic loader and library start (`brk` 3, `mmap` 8, `mprotect` 3, `munmap` 1, `fstat` 4, `pread64` 2, `arch_prctl`, `set_tid_address`, `set_robust_list`, `prlimit64`, `getrandom`, `rseq`, `access` which fails with `ENOENT` for `/etc/ld.so.preload`, plus `openat` and `close` of the library and its cache); your code: `openat` of `/etc/hostname`, `read` (two: the data, then end of file), `close`, and `write`. The second error is `ioctl(1, TCGETS)` which `stdio` uses to ask whether stdout is a terminal; it fails with `ENOTTY` on a file. Your code accounts for about 6 of the 40 calls (`openat`, `fstat`, two `read`, `close`, `write`); the rest is the runtime. Measured: with stdout a pipe the same program made 39 calls and 1 error (no `ioctl`), with stdout `/dev/null` 40 and 2. On a terminal `ioctl` succeeds and the library switches to line buffering, so there would be three `write` calls instead of one (from memory, not run here, since the harness has no terminal): the count depends on where stdout goes.

**D.** Use the loop in `d6_cost.c` (section 5): about 82 ns for the raw call and about 21 ns for the vDSO call, a ratio of about 4. The vDSO call is a user-mode function that reads a kernel-maintained data page; the raw call pays the mode switch, register save and restore, argument validation and mitigations. With `mitigations=off` the system call gets cheaper (the kernel skips the speculation barriers and, on a CPU that needs it, page-table isolation); the vDSO call does not change because it does not enter the kernel. The size of the change depends on the CPU. This guest could not be rebooted with different options, so the effect is not measured here.

**E.** The solution, with its output (the last line is the exit status, which is `argc`, here 4: the program name and three arguments):

```c
/* Problem E: no libc. Print every argument, one per line, then exit with the argument count. */
static long sys3(long nr, long a, long b, long c)
{
    long ret;
    __asm__ volatile("syscall" : "=a"(ret) : "a"(nr), "D"(a), "S"(b), "d"(c) : "rcx", "r11", "memory");
    return ret;
}

static unsigned long len(const char *s)
{
    unsigned long n = 0;
    while (s[n])
        ++n;
    return n;
}

/* The kernel starts the program with rsp pointing at argc, then argv[0..argc-1], then NULL.
   _start is not a C function (there is no return address), so a small assembly stub passes rsp on. */
void c_start(long *sp)
{
    long argc = sp[0];
    char **argv = (char **)(sp + 1);
    for (long i = 0; i < argc; ++i) {
        sys3(1, 1, (long)argv[i], (long)len(argv[i]));
        sys3(1, 1, (long)"\n", 1);
    }
    sys3(60, argc, 0, 0);
}

__asm__(".globl _start\n"
        "_start:\n"
        "    mov %rsp, %rdi\n"
        "    and $-16, %rsp\n"
        "    call c_start\n");
```

```text
./pe
one
two words
three
exit status 4
```

What goes wrong: with `-nostdlib` GCC recognised the `len` loop as `strlen` and emitted a call to it, and the link failed with `undefined reference to strlen`. That was measured: the first build failed with exactly that message, and adding `-fno-builtin` fixed it. The other points: `_start` is not a function (nothing returned to it, no return address is pushed), so it is written as a small assembly stub that passes the initial `rsp` to a C function as `sp`; `argc` is `sp[0]` and `argv` starts at `sp + 1`; the stack is aligned to 16 bytes before the call as the calling convention requires; and the program must end with the `exit` system call, because returning from `_start` would run into whatever follows.
